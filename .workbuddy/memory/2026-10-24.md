## 今天踩到 / 探明的技术坑（重要）

1. **`Pages` 是「字符串数组」，每条要再 `json.loads` 一次**。漏了这步拿到的是转义乱码。
2. **"查不到"不能用"返回 0 条"判断**——搜索引擎对任何输入都返回结果。
   实测编造句"红枣配薄荷能排肝毒"照样返回 10 条，最高分 0.73；
   真说法"隔夜菜亚硝酸盐"最高 0.78。**分差 0.05，等于没有分界**。
3. **只看 score 会更信营销号**：编造说法得分最高的那条来自「我爱偏方网」，
   第二「35健康」。必须先用信源分级压掉，再谈判定。
4. 信源分级实测区分度：编造说法 10 条里 7 条被剔除、可信独立站点仅 3 个；
   真说法（隔夜菜/红枣补铁）可信独立站点 7—9 个、剔除 0 条。这个信号可用。
5. 光有分级还不够：编造说法仍捞到「四川省中医药管理局」一条（内容无关的发布会实录）。
   所以判定层必须再加一步「这条来源到底有没有在说这件事」。

### 今天新踩到的坑（关键）
1. **拆出来的命题必须是断言句，不能是问句**。问句无法被支持/反驳，判定就没有主语。
2. **拆解必须覆盖「存在层 + 效力层」两层**。只拆效力层 → 一律判"相反"，把话说死反而不准。
   正解：红枣含铁（真）+ 吃红枣不能有效补铁（假）→ 整体 部分有据。这才是有层次的诚实。
3. **整体结论的汇总规则必须写死在 prompt 里**，不能让模型自由发挥：
   存在层成立 + 效力层相反 → partial，不是 contrary。
4. **必须做结论缓存**（`cache/check/`）。同一句话两次跑出不同结论 = 事故。缓存后回放完全稳定，也省调用。
5. **来源要去重两次**：一次按 URL，一次按「标题+日期」。
   中国新闻网有简繁两版、PC/移动两版，域名不同但同一篇。只按 URL 去重会把它算成两个独立来源，
   等于自己打自己脸——说好了"只数独立来源"。

## 15:40—16:00 性能优化（结论：瓶颈不在代码里）

### 实测分阶段耗时（权威数据，以后别再靠猜）

| 阶段 | 耗时 |
|---|---|
| 拆命题（模型） | 25~33 秒 |
| 并发搜索（6~9 条） | **0.7~1.3 秒** |
| 古籍检索（877 万字） | 1.0~1.2 秒 |
| 判定（模型） | 19~34 秒 |

**关键结论：搜索根本不是瓶颈，两次模型调用才是。**
之前我判断"搜索串行 15~30 秒"是错的——那时搜索走了缓存所以快，我误以为是串行的功劳。
现在改成并发是真优化（未命中缓存时有效），但对端到端影响很小。

### 做了什么
1. 搜索串行 → 并发（ThreadPoolExecutor，6 线程）：`fetch_queries` / `assemble_modern` / `gather_modern_batch`
   - `wsa_search._usage_bump` 加了线程锁，否则并发写 `_usage.json` 会丢数/写坏
2. **修了一个真 bug**：`llm_client.load_config()` 只返回 `model`，把 `fast_model` 丢了
   → 拆命题一直退回慢模型。配置写对了但没读到，比没写更坑
3. 新增 `warmup()`：网关冷启动实测 **首次 13.9s / 二次 2.4s**；`app.py` 启动时后台预热
4. 判定输入来源 10→8、摘要 300→220 字、max_tokens 1200→900
5. 新增 `stats.stages` 分阶段耗时，路演被问"为什么快/慢"有据可答

### 优化后仍慢的原因（要如实讲）
网关在比赛期间被全国 50 多城选手同时使用，排队严重。
实测同一模型只回 2 个字：13.9s → 2.4s → 27s（随时段波动）。
**这不是代码能解决的。** 别再承诺"优化到 12 秒"。

### 真正的对策：让演示不依赖网关
预核 6 条常见家族群说法进缓存（约 5 分钟 + 54 次搜索）：
隔夜水不能喝 ◐ / 微波炉致癌 ∅ / 菠菜补铁 ◐ / 味精加热致癌 ✕ / 一天两蛋 ◐ / 蜂蜜水通便 ✕

## 16:30 更正一个错误归因（重要，别再犯）

**我说过的话**：「全国 50 多个会场在抢同一个网关」。
**这是猜的，没有证据。** 用户追问后重新实测，结论完全不同：

### 实测数据
同一模型、同样只要 5 个 token，连续 6 次：
`2.4s / 7.6s / 7.7s / 7.3s / 7.3s / 7.1s`
→ **5/6 次稳定在 7.1–7.7 秒**。如果是"别人在抢"，应该忽高忽低；现在是稳定地慢。

换模型也没用（真实拆命题任务，不是试探）：
| 模型 | 基线(5 token) | 真实拆命题 |
|---|---|---|
| gpt-6-luna | 8.5s | — |
| gpt-5.6-luna | 6.6s | — |
| gpt-6-astra | 2.8s（单次，属偶发） | **23.0s / 29.2s** |
| gpt-6.1-sol | 7.3s（中位） | 31.8s |

**结论：慢是结构性的——这类重模型本身每次调用就要 20~30 秒，跟同时在线多少人基本无关。
换模型也压不下来，没有轻量档可选（网关只给 gpt-5.6/6.x 这一档）。**

### 教训
- 不要用"合理的推测"充当"测得的事实"。
  延迟高 → 直接归因到"比赛人多"，听起来合理，但我一次都没验证过
- 用户会追问，而且一问就露。以后凡是归因类结论，先测再说，测不了就说"不知道原因"
- 已经在 README 里把错的那句改成："这一类重模型的推理开销，与同时在线人数基本无关"

### 实际影响：对策不变
缓存 + 异步两步，跟慢的原因是什么无关，都成立。

### 又修了一个会误导评委的地方（重要）
判「查不到」那一屏，古籍区原标题是「在 39 部古籍中找到 39 处记载」。
评委第一反应必然是：都找到 39 处了，凭什么说查不到？
真相：那 39 处是大枣、薄荷**各自**的词条，不是「红枣配薄荷能排肝毒」这个说法。

改法：在 `checker.py` 加 `_polish(r)`，判 not_found 且古籍有命中时，
标题改成「39 部古籍里提到过这些药材，但没有「XXX」这个说法」。
**关键：`_polish` 放在 `_read_result` 里调用**，这样走缓存和实时计算两条路径都生效，
不用重新跑一遍（重跑要 60s+ 且烧额度）。
