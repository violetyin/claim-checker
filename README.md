# 这句能信吗 · 双源核查

> 丢一句你听来的养生说法进去，它把这句话拆成几个可独立核验的命题，分别去查
> **古书里有没有这句话**、**现代权威怎么说**，然后告诉你哪句有据、哪句是方向对但被夸大、哪句根本查不到。
> 每条结论都挂着点得开的来源。

1024 超能 Coding 周末 · 武汉会场 · 侦探赛道（元宝搜索）

**在线版本（可直接输入任意说法查）**：https://claim-checker.app.workbuddy.host/?sharecode=6YMIOE5PWZ

　完整版已部署上线：输入框、拆命题、双源检索、五档判定全部在云端真实运行。
　预核过的常见说法约 5 秒返回；全新说法 30~120 秒（取决于模型网关当时的排队情况）。
　不需要任何密钥，也不需要本地环境。

## 一、它解决什么问题

家族群里每天都在转这类话：

- 「隔夜菜致癌」
- 「红枣补铁」
- 「绿豆解百毒」
- 「红枣配薄荷能排肝毒」（编的）

这些说法有个共同点：**不是全对，也不是全错**。它们通常有一半是真的，另一半被夸大了。
而现有 AI 工具在这个场景上有个系统性毛病——**什么都能答**。你问它一个编出来的说法，它也给你一串听起来很专业的解释。

这个作品反过来做两件事：

1. **分出程度**：不是判「对/错」，而是判「对到什么程度」
2. **敢说不知道**：查不到就明确说查不到，不硬编

## 二、五档结论

| 档位 | 含义 | 例子 |
|---|---|---|
| ✓ 有据 | 多个独立权威来源一致支持 | 红枣含有铁元素 |
| ◐ 部分有据 | 方向对，但程度、范围或适用条件被夸大 | 红枣补铁 —— 含铁是真的，能有效补铁是假的 |
| ✕ 相反 | 权威来源的结论与说法相反 | 吃红枣能有效补充人体所需的铁 |
| ❖ 仅古载 | 古籍有记载，但现代权威支持不足 | 《本草纲目》里的某些食疗说法 |
| ∅ 查不到 | 给定来源里没有一条真在说这件事 | 红枣配薄荷能排肝毒 |

**养生传言绝大多数落在「部分有据」这一档。** 能把这档单独拎出来，是这个作品与「什么都能答的 AI」最本质的区别。

## 三、四步流程

```
你输入一句话
   │
   ├─ ① 拆　LLM 把话拆成 2~3 个可独立核验的命题
   │        必须覆盖两层：存在层（有没有这东西）+ 效力层（效果有多大）
   │        每个命题生成 3 条检索式：正面查 / 反面查 / 限定权威源
   │
   ├─ ② 查　双源并行
   │        ├─ 现代：元宝搜索（SearchPro）→ 10 条结果/检索式
   │        └─ 传统：42 部本草古籍全文检索（877 万字，本地）
   │
   ├─ ③ 比　信源分四级，只采信 T1/T2
   │        数的是「独立域名」，不是「结果条数」
   │        同一篇文章的简繁两版、PC 与移动版算一个来源
   │
   └─ ④ 判　LLM 读完全部证据后给五档结论
            硬规则：来源里没有一条直接支持 → 必须判「查不到」
```

## 六、五个关键设计决策

### 1. 「查不到」不能用「返回 0 条」判断

这是做这个作品最重要的一个发现。

搜索引擎对**任何**输入都会返回结果。实测编造的说法「红枣配薄荷能排肝毒」照样返回 10 条，
最高相关性 0.73；而真实说法「隔夜菜亚硝酸盐」最高 0.78。**分差 0.05，等于没有分界。**

更麻烦的是：编造说法得分最高的那条来自「我爱偏方网」，第二名「35健康」——
都是营销号。**只看分数，系统反而更信不可靠的来源。**

所以「敢认输」不能指望搜索引擎，只能自己判：先把信源分级压一遍，再让模型读摘要判断
「有没有人真的在说这件事」。

### 2. 拆命题必须拆出「存在层」

一开始只拆效力层（「红枣含铁量丰富吗」「铁容易吸收吗」），两条都被反驳，整体判成「相反」——
把「红枣补铁」一棍子打死了。但这句话本身**有真有假**：

- 红枣含有铁元素 → 真
- 吃红枣能有效补铁 → 假

只拆效力层，判定就丢了层次，也不准。加上存在层之后，整体才能落在「部分有据」。

### 3. 命题必须是断言句，不能是问句

问句（「含铁量是否丰富」）无法被支持或反驳，判定就没有主语了。
这个问题是在实测中被发现的，不是设计时想到的。

### 4. 结论必须落盘锁定

同一条说法连跑两次，模型给过「部分有据」也给过「相反」——
因为拆出来的命题、检索式、拿到的来源每次都不同。

评委会上出这种事故作品就废了。所以结论整体落盘到 `cache/check/`，
第二次起完全一致，界面上标「回放 / 实时」，不装实时。

**附带一个好处：现场断网也能演示。** 整条结论（含模型判定）都在本地 JSON 里。

### 5. 云端必须异步，同步请求一定被掐断

部署上线后发现：云端反向代理约 **100 秒**就返回 `524 Response Timeout by Origin Server`。
而一条新说法在网关拥塞时要 60~120 秒——同步请求会被拦腰砍断，用户看到的是报错页，
可后台其实还在跑。

现在拆成两步：

```
/api/start?q=…   → 立刻返回 running，后台线程开始核（命中缓存则直接 ready）
/api/poll?q=…    → 每 2 秒问一次；结果一落盘就读到，不依赖那根请求还活着
```

前端会显示已等待秒数。这样无论上游多慢，用户看到的都是「还在查」，
而不是「出错了」。同一个说法重复点击不会重复烧额度（有在跑标记）。

## 七、信源分级规则

| 档 | 范围 | 能否进证据链 |
|---|---|---|
| **T1 权威** | 各级 `.gov.cn`、卫健委、疾控、中国营养学会、`nhc.gov.cn`、人民日报、新华社、央视、光明网、高校 `.edu.cn`、中科院 `.ac.cn`、腾讯医典 | 可单独支撑结论 |
| **T2 可信** | 地方主流媒体、机构科普（科普中国、中国数字科技馆）、医院、学会 | 需两条以上互相印证 |
| **T3 一般** | 商业健康站、聚合平台（35健康、百度健康、今日头条、知乎） | 只作线索，不作证据 |
| **T4 剔除** | 偏方站、养生营销号（我爱偏方网、苹果绿、各类「老中医说」） | 直接剔除 |

实际效果：编造说法「红枣配薄荷能排肝毒」的 55 条结果里，**43 条被剔除**。

## 八、合规边界

- 只做资料核对，**不提供诊疗建议，不替代医生**
- **不做**疾病诊断、不给用药或停药建议
- 古籍文献记载 **≠** 现代临床疗效证据，两者在页面上分开标注、不互相替代
- 只谈营养学范畴：食材成分、膳食指南、研究结论强度
- 不宣称「排毒」「治愈」「根治」
- 不碰孕期、儿童、急症
- 不碰时政、不碰个人隐私信息

## 十、已知限制

1. **新说法要 30~120 秒**，瓶颈在模型网关，不在本地。实测分阶段：

   | 阶段 | 耗时 | 说明 |
   |---|---|---|
   | 拆命题（模型调用） | 25~64 秒 | 这一类重模型的推理开销，与同时在线人数基本无关 |
   | 并发搜索（6~9 条） | **0.7~1.3 秒** | 已从串行改为并发，不是瓶颈 |
   | 古籍检索（877 万字） | 0.1~1.2 秒 | 内存内匹配 |
   | 判定（模型调用） | 19~56 秒 | 上游排队 |

   网关冷启动实测：同一模型第一次调用 13.9 秒、第二次 2.4 秒。
   服务启动时会自动预热两个模型；云端请求已改为异步轮询，不会被反代超时掐断。

   **预核过的说法约 5 秒返回**（走结论缓存，不碰网关）。

2. **只覆盖养生/营养话题**。输入时政、医疗诊断类问题不在设计范围内。
3. **古籍检索按关键词召回**，命中不等于「这句话有出处」——所以古籍原文照给，
   由模型读原文判断，页面上也明确写出这一点。
4. **元宝搜索标准版无 `authority_level` 字段**，权威度靠自建信源分级实现；
   若升级旗舰版，可叠加官方的权威度打分。
5. 判定仍依赖模型，极端情况下会有档位偏差。已用「硬规则 + 结论落盘」降低影响。

## 十一、额度与成本

- 元宝搜索活动期 6000 次/自然月（日常 2000 次/月）
- 一次完整核查 ≈ 6~9 次搜索 + 2 次模型调用
- 全部查询结果按 `query → JSON` 落盘缓存，重复调用不消耗额度
- 客户端**只允许一次重试**，没有无退避的重试循环（避免调试时烧光额度）
- 今日开发消耗：约 83 次
